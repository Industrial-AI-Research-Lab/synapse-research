# Навигатор доказательств для химических документов

Монорепозиторий с независимыми frontend и backend для работы с научными статьями, лабораторными отчётами и технической документацией. Пользовательский сценарий — химик-исследователь задаёт сложный вопрос к своему корпусу файлов, находит первоисточники, проверяет условия экспериментов и получает только подтверждённые факты с цитатами.

ПАВ и EOR — демонстрационная предметная область, а не ограничение продукта. Текущий встроенный корпус синтетический и нужен для демонстрации процесса. Он **не является** доказательством для производственной приёмки: до такой приёмки необходимо загрузить и верифицировать первичные технические документы заказчика.

## Структура

```text
backend/   FastAPI API, Clean Architecture и корпус данных
frontend/  React 18 + TypeScript + Vite + SCSS Modules
.agents/   локальные skills и соглашения для дальнейшей разработки
```

## Пользовательский сценарий MVP

1. Химик открывает «Мои документы», загружает документ с извлекаемым текстом и выбирает корпус для поиска.
2. Он задаёт исследовательский вопрос, например: «Какие ПАВ показали устойчивость эмульсии при pH 5–7?».
3. Система локально находит релевантные фрагменты, показывает документ, его позицию (страницу, запись, строку или фрагмент) и текст цитаты. Это кандидаты на доказательства, а не готовый научный вывод.
4. Эксперт сверяет фрагмент с первоисточником, вручную извлекает условия, методику и результат, затем отправляет запись на проверку.
5. Только выпущенные проверенные факты участвуют в ответе на вопрос: интерфейс показывает краткий вывод, условия опыта, источник и ограничения сопоставимости.

### Локальный корпус документов

Вкладка «Мои документы» (`/documents`) поддерживает загрузку, локальный поиск и скачивание первоисточника. Можно добавлять PDF с извлекаемым текстом, JSON/JSONL/NDJSON, CSV/TSV, XML (включая JATS/NXML и TEI), HTML, TXT/Markdown, RIS и BibTeX. Для PDF цитата ведёт на страницу; для структурированных файлов — на запись, строку или фрагмент. Сканированные PDF без текстового слоя пока возвращают понятную ошибку — OCR является следующим отдельным этапом.

Загрузка не ограничена размером файла, числом документов в библиотеке, количеством страниц или записей и объёмом извлечённого текста, включая отдельную запись или страницу. Прежние настройки `DOCUMENT_MAX_*` больше не применяются. Фактический объём обработки зависит от доступной памяти и диска. Ошибки загрузки показываются в toast-уведомлении с именами файлов и причинами; файлы с ошибками остаются выбранными для повторной попытки.

Если `DOCUMENT_ACCESS_TOKEN` не задан, доступ открыт для локальной разработки. При заданном значении документы, история исследований и запуск исследований обоих видов используют общий код команды: API ожидает `Authorization: Bearer <код>`. Интерфейс хранит введённый код в текущей вкладке браузера (`sessionStorage`). Инструкции по production-настройке находятся в [deploy/README.md](deploy/README.md). Документы не становятся числовыми фактами автоматически.

Backend сохраняет REST-контракт на `/api`: `health`, `evidence`, `analysis` и интеграцию с Synapse. Frontend обращается к нему через Vite proxy в разработке либо через `VITE_API_BASE_URL` в другом окружении.

### Исследование в Synapse по выбранным документам

На странице `/documents` основное действие «Запустить исследование в Synapse» передаёт вопрос и отмеченные поддерживаемые файлы в существующий workflow Synapse. Учётные данные Synapse остаются на backend: он создаёт проект через `POST /api/projects` и прикладывает файлы multipart-полем `files`. После запуска PAV открывает сохранённое исследование в разделе «Исследования». Запуск по выбранным опытам из доказательной базы ведёт в тот же раздел.

Для DevStand нужны отдельные API-учётные данные Synapse (вход в Edge сам по себе их не передаёт backend'у PAV):

```dotenv
SYNAPSE_URL=https://dev.synapse.bonpp.com
SYNAPSE_UI_URL=https://dev.synapse.bonpp.com
SYNAPSE_USER=<email сервисного пользователя DevStand>
SYNAPSE_PASSWORD=<пароль или пароль приложения>
SYNAPSE_WORKFLOW_ID=<обычный workflow для существующей интеграции>
SYNAPSE_DOCUMENT_WORKFLOW_ID=<UUID workflow из DevStand>
SYNAPSE_DOCUMENT_RUN_CONFIG_ID=agent-owned-models
```

`SYNAPSE_DOCUMENT_WORKFLOW_ID` позволяет не менять текущий обычный workflow: именно он должен указывать на workflow, который собирает исследовательский ответ. `SYNAPSE_DOCUMENT_RUN_CONFIG_ID=agent-owned-models` сохраняет модели, заданные агентами workflow, вместо дефолтной модели тенанта. API и интерфейс должны относиться к одному экземпляру Synapse: старый локальный сервер может не поддерживать workflow DevStand и не иметь доступа к его файлам. Для workflow с согласованиями используйте `SYNAPSE_APPROVAL_MODE=human`. После изменения `.env` перезапустите backend. Файлы выбранного корпуса будут отправлены в DevStand при каждом запуске исследования.

### Общая история исследований

Раздел «Исследования» (`/researches`) сохраняет **новые запуски из PAV** по документам и по опытам в общей истории команды. Старые проекты Synapse не импортируются; личных историй и отдельных учётных записей в этом сценарии нет. Свежие записи отображаются первыми, список можно отфильтровать по типу и состоянию.

Страница `/researches/:id` показывает исходный вопрос, выбранные источники, состояние, этап и время последней успешной проверки. Если workflow ждёт решения, команда видит запрос и его данные, может добавить комментарий и подтвердить либо отклонить запрос. Вместе с решением frontend передаёт просмотренный снимок `expected_data`. Перед отправкой backend заново проверяет его актуальность; при изменении данных, ошибке связи или уже обработанном запросе решение не отправляется. Synapse получает тот же снимок и проверяет его при записи решения. Ошибка решения остаётся на экране после автоматического обновления статуса. PAV использует существующий API подтверждений Synapse без изменений Synapse. Переписка с агентами и технический журнал доступны по ссылке «Открыть подробности в Synapse».

Полученный итоговый ответ сохраняется целиком. HTML-отчёт открывается во встроенной изолированной области просмотра; при наличии HTML текстовая версия раскрывается отдельно. Созданные материалы можно скачать, а опубликованный отчёт — открыть по внешней ссылке, если Synapse предоставил её. Ответ исследования не становится автоматически выпущенным лабораторным доказательством.

Идентификаторы файлов отчёта извлекаются из сохранённых JSON-ответов агентов текущего запуска. PAV не использует имена узлов workflow как идентификаторы элементов execution trace: этот API Synapse принимает другие идентификаторы. Метаданные файла в Synapse ещё не подтверждают доступность его содержимого; ошибка скачивания показывается отдельно и не стирает уже сохранённые материалы.

История проверяет состояние активных исследований каждые 30 секунд, пока страница открыта; карточка исследования — каждые 10 секунд до финального состояния. В обоих случаях доступно ручное обновление. При сбое Synapse PAV показывает ошибку рядом с сохранёнными данными и последним временем успешной проверки. Отдельного фонового опроса при закрытом интерфейсе нет.

### API и хранение истории

Оба прежних endpoint запуска дополнены необязательным `request_id` в формате UUID. Frontend передаёт UUID при каждом новом запуске, а ответ содержит `research_id` для перехода в историю. Повтор API-запроса с тем же UUID и тем же вопросом, типом и источниками возвращает сохранённую запись без повторного создания проекта; другой набор данных с тем же UUID возвращает `409`. Если результат отправки неизвестен, запись остаётся в истории со статусом `start_unknown`: перед новым запуском следует проверить проекты в Synapse.

Создание проекта в Synapse может занять несколько минут. В примере конфигурации `SYNAPSE_TIMEOUT=300`; при тайм-ауте создания PAV предупреждает о неизвестном результате отправки и предлагает сначала проверить историю Synapse.

При отказе Synapse PAV сохраняет и показывает исходное сообщение ответа вместе с HTTP-кодом и адресом операции. Структурированные ошибки сохраняют свои поля; причины остановки исследования берутся из сообщений Synapse без пересказа. Ответ запуска также содержит `sync_error`. Пароль сервисной учётной записи и известный токен скрываются в HTTP-ошибках, тела ответов не попадают в журнал трассировки. Если ответа Synapse нет (например, при тайм-ауте), PAV сообщает о сбое связи. В старых записях, где был сохранён только HTTP-код, исходное сообщение восстановить без повторного обращения нельзя.

| Метод и маршрут | Назначение |
| --- | --- |
| `POST /api/documents/research` | Запуск по документам: `query`, `document_ids` (1–50), `request_id` |
| `POST /api/synapse/projects` | Запуск по опытам: `question`, `experiment_ids` (до 30), `request_id` |
| `GET /api/researches` | Сохранённая история; необязательные фильтры `kind=documents\|evidence` и `research_status` |
| `GET /api/researches/{research_id}` | Полная сохранённая запись с ответом, источниками, материалами и запросами решений |
| `POST /api/researches/{research_id}/refresh` | Чтение актуального состояния Synapse и сохранение результата |
| `POST /api/researches/{research_id}/approvals/{approval_id}` | Решение: `approved` и необязательный `feedback` (до 5000 символов) |
| `GET /api/researches/{research_id}/files/{file_id}` | Скачивание созданного материала из серверного кеша или Synapse |

`ResearchService` сохраняет записи через `SqliteResearchRepository` в `researches.sqlite3` внутри `DOCUMENT_STORE_DIR`. По умолчанию это `backend/data/documents/researches.sqlite3`; в локальном Compose существующий bind mount `backend/data` сохраняет базу при пересоздании контейнера. Production Compose использует `/service/var/documents` и постоянный том `document_store`, в котором также находится база истории. При переопределении `DOCUMENT_STORE_DIR` каталог должен находиться в постоянном хранилище. Резервная копия документного каталога должна включать базу истории.

В SQLite хранятся вопрос, идентификаторы и названия документов, снимки выбранных опытов, состояние, полный ответ и кеш файлов. При обновлении отчёты скачиваются сразу, остальные материалы — после завершения исследования либо при первом скачивании. Лимит одного скачиваемого материала — 20 МиБ. Ошибка скачивания сохраняет список материалов и ранее полученный ответ; уже кешированные файлы доступны при последующей недоступности Synapse. Название удалённого исходного документа остаётся в истории, но его оригинал PAV не дублирует в базе исследований и не сможет скачать после удаления из корпуса.

Автоматические проверки используют синтетический Synapse gateway и отдельный документный корпус. Дополнительно на DevStand проверены исходный workflow через dry-run без применения конфигурации и сохранение реального завершённого исследования: полный ответ на 43 551 символ и все 18 материалов прочитались из отдельной базы после перезапуска без связи с Synapse. Новый контрольный запуск из интерфейса PAV прошёл согласования документов и онтологии, построил индекс, извлёк факты и собрал коллекцию. Дальнейшее выполнение остановилось: в настройках `knowledge_collection_v2` проверка `collection_ready` требует минимум два пакета фактов и две их контрольные суммы, а по одному документу создан один пакет. Код и настройки Synapse не изменялись. Полный новый запуск до итогового отчёта не подтверждён.

При остановке PAV сохраняет причину из итогового сообщения агента текущего запуска и показывает её в карточке. Причина и уже полученные материалы остаются доступны после перезапуска и ошибки связи с Synapse.

## Открытые источники

Страница «Каталог источников» (`/sources`) при каждом открытии вызывает `GET /api/public-sources`: сервис проверяет ссылки из курируемого каталога и ищет свежие русско- и англоязычные библиографические записи в открытом каталоге Crossref. Поиск строится вокруг ПАВ и химических методов увеличения нефтеотдачи: керновых опытов, ПАВ-полимерного и щёлочь‑ПАВ‑полимерного заводнения, адсорбции, межфазного натяжения и реологии. Источники открываются по ссылке в отдельной вкладке.

У каждого источника есть роль: лабораторные данные, методика, обзор или контекст кейса. «Татнефть» — только метка кейса, а не ограничение поиска.

Новые находки имеют статус «нужна проверка». Они не становятся числовыми фактами и не участвуют в инженерном сравнении автоматически. Чтобы выпустить результат из статьи или патента в `/api/evidence`, эксперт должен проверить условия измерения, методику и точный фрагмент первоисточника.

### Ручная проверка опыта

Для материалов из каталога доступен минимальный рабочий поток: «Добавить опыт» → заполнение рецептуры, условий, методики, результата и цитаты → очередь проверки → «Подтвердить и выпустить». Заявки сохраняются в `backend/data/evidence_reviews.json`. Пока заявка ожидает проверки, она не возвращается через `/api/evidence` и не участвует в анализе. После подтверждения ей присваивается статус `released`, и она сразу становится частью доказательной базы.

В этой первой версии нет аутентификации и разделения ролей: экран проверки предназначен для внутреннего процесса, а подтверждение выполняет пользователь, который вручную сверяет запись с первоисточником.

## Приёмочные критерии ТЗ

Экран `/quality` и API `GET /api/quality/report` рассчитывают четыре проверяемых критерия:

- выпуск числового факта возможен только при наличии методики, условий измерения и ссылки на фрагмент источника;
- полнота выпущенных записей относительно проверенного корпуса — не менее 80 %;
- контрактная проверка контрольных вопросов — не менее 85 %;
- повторный `/api/analysis` выполняется локально, без автоматического создания задачи в Synapse.

Запись, не прошедшая первый критерий, помещается в карантин и отсутствует в `/api/evidence`. Встроенный пример содержит `LAB-005` именно как такую запись: значение не выдаётся инженеру, пока владелец данных не добавит методику и проверяемую ссылку на фрагмент.

Для реальной приёмки замените `backend/data/evidence.json` и `backend/data/control_questions.json` на верифицированный корпус: ссылки должны вести на неизменяемые фрагменты исходных документов, `source.origin_type` должен быть равен `primary_technical_document`, а контрольные вопросы и ожидаемые факты — утверждены профильным экспертом. Отчёт явно блокирует производственный статус для каждой записи с другим происхождением источника.

## Запуск

1. Запустите backend: `docker compose up --build backend`.
2. В отдельном терминале перейдите в `frontend`, выполните `npm install`, затем `npm run dev`.
3. Откройте `http://localhost:5173`.

Для Synapse скопируйте `.env.example` в `.env` и заполните параметры. Секреты не добавляйте в репозиторий.

## Проверки

- Frontend: `cd frontend && npm run lint && npm run build`
- Backend: `pytest backend/tests` в настроенном Python-окружении или проверка API внутри контейнера.
- Приёмка: `curl http://localhost:8091/api/quality/report` и проверка всех `passed: true`. Отдельно убедитесь, что `production_ready: true` только после загрузки реального корпуса.

## Production и CI/CD

Проект разворачивается как один monorepo: React frontend и FastAPI backend
собираются в отдельные образы, но публикуются и выкатываются одной версией
коммита. Инструкции по первичному запуску VPS, настройке HTTPS и GitHub Actions
находятся в [deploy/README.md](deploy/README.md).
